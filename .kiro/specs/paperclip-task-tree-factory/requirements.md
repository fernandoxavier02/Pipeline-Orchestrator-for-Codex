# Requirements

**Version:** 0.1.0
**Date:** 2026-06-12
**Status:** approved

## Introduction

The Paperclip task tree factory turns Pipeline Orchestrator workflows into Paperclip issue trees. It does not execute the local Codex pipeline; it creates or describes Paperclip cards whose dependencies mirror the standalone flow.

This spec captures the repo-local contract for that factory so Wave 6B can close the missing Kiro spec gap without making unsupported claims about Marketplace publication, installed Codex cache activation, or live VPS execution.

## Glossary

- **Task_Tree_Factory:** The combined pure and I/O modules under `references/paperclip/spec/lib/**` that classify, template, construct, and optionally create Paperclip issues.
- **Flow_Template:** A declarative workflow shape from `tree-template.cjs`.
- **Node_Spec:** The payload for one Paperclip issue generated by `tree-factory.cjs`.
- **Fan_In_Node:** A join card whose `blockedByIssueIds` requires multiple upstream cards to complete.
- **Dry_Run:** A `grow-tree` run without `--confirm`; it must not perform Paperclip `POST /issues`.
- **Repo_Only_Evidence:** Source, docs, and tests in this repository. It is not proof that the installed plugin or Paperclip server changed.

## Requirements

### REQ-001: Preserve the Canonical Flow Inventory

**User Story:** As a maintainer, I want the task tree factory to describe every supported Paperclip flow from the flow mirror, so that missing or stale flow templates are visible before dispatch.

#### Acceptance Criteria

1. WHEN the spec names the supported flow set, THE Task_Tree_Factory SHALL include bugfix, feature, user-story, audit, ux, spec, hotfix, and review-only families.
2. WHEN a family has light and heavy variants in `PAPERCLIP-FLOW-MIRROR.md`, THE Task_Tree_Factory SHALL document both variants.
3. IF a historical compatibility template such as `SIMPLES`, `MEDIA`, or `COMPLEXA` is preserved, THEN THE Task_Tree_Factory SHALL identify it as compatibility behavior rather than the current canonical flow set.

### REQ-002: Keep Issue Dependencies Explicit

**User Story:** As an operator reviewing Paperclip cards, I want every generated card dependency to be explicit in `blockedByIssueIds`, so that the execution order is observable without relying on prose.

#### Acceptance Criteria

1. WHEN a linear node follows a previous node, THE Node_Spec SHALL include the previous issue id as its only blocker.
2. WHEN a fan-in node joins parallel siblings, THE Node_Spec SHALL include every required sibling issue id.
3. IF any fan-in sibling id is missing from the step map, THEN THE Task_Tree_Factory SHALL fail instead of creating a partial join.

### REQ-003: Enforce Dry-Run Before Mutation

**User Story:** As a user dispatching work to Paperclip, I want the first pass to be a dry-run, so that no remote issue is created before explicit confirmation.

#### Acceptance Criteria

1. WHEN `grow-tree` runs without `--confirm`, THE CLI SHALL return JSON describing the next card and SHALL NOT call `POST /issues`.
2. WHEN `grow-tree` runs with `--confirm`, THE CLI MAY create Paperclip issues after validating company id, role id, and roster lookup.
3. IF the Paperclip API returns a successful status without an issue id, THEN THE CLI SHALL refuse to report success.

### REQ-004: Validate External Identifiers Before I/O

**User Story:** As a maintainer, I want Paperclip ids validated before network calls, so that malformed or injected ids cannot reach the transport layer.

#### Acceptance Criteria

1. WHEN `companyId` or agent id is used for a Paperclip request, THE I/O layer SHALL validate it against the safe id contract before the request.
2. IF an id fails validation, THEN THE I/O layer SHALL throw a descriptive error and SHALL NOT call the transport.
3. WHEN tests use a fake transport, THE same validation contract SHALL still run.

### REQ-005: Measure Fidelity Separately From Dispatch

**User Story:** As a reviewer, I want fidelity measurement to be a separate reportable operation, so that measuring the tree does not mutate Paperclip state.

#### Acceptance Criteria

1. WHEN `measure-paperclip-fidelity` runs, THE operation SHALL read available flow evidence and report fidelity without creating Paperclip issues.
2. WHEN fidelity gaps are found, THE report SHALL distinguish missing flow coverage, missing role inventory, and unsupported live execution proof.
3. IF only repo evidence is available, THEN THE report SHALL label the result as repo evidence and SHALL NOT claim live Paperclip execution.

### REQ-006: Keep Public Claims Within the Proven Evidence Layer

**User Story:** As the repository owner, I want the spec to distinguish repo, package, installed cache, and live Paperclip evidence, so that Wave 6B cannot close with an overstated parity claim.

#### Acceptance Criteria

1. WHEN this spec closes, THE closeout SHALL state whether evidence is repo-only, package-surface, installed-cache, or live-smoke.
2. IF Marketplace publication, installed cache sync, or VPS Paperclip execution is not performed, THEN THE closeout SHALL explicitly say it is not proven.
3. WHEN docs or examples cite Paperclip behavior, THE docs SHALL reference runtime-backed modules or tests rather than unsupported narrative promises.
